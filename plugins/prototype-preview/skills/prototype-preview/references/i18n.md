# Connecting the Language setting to the app's copy

The panel's Language control sets `useDevSettings().language`. The copy only changes if whatever renders the copy follows that value. Find out what the app uses now: check `package.json` for `i18next`, `react-i18next`, `expo-localization`, `@lingui/*` or `react-intl`, and look for a `locales/`, `i18n/` or `translations/` folder.

In every case, make the `language` options in `devSettings.ts` exactly the languages the app has copy for. A language in the panel with no copy behind it just shows the fallback, which reads like a bug.

## A. No i18n yet

Install with `--with-i18n`. That adds `<source-root>/i18n/index.ts` (`useI18n()`, giving `t`, `formatNumber` and `formatDate`) and `en.ts`. `index.ts` imports `../preview/devSettings`, so keep `i18n/` and `preview/` side by side.

1. Move the screens' user-facing strings into `en.ts`, with keys grouped by screen (`'home.title'`), and replace them with `t('home.title')`. Leave out accessibility-only debug strings and anything that isn't copy.
2. For each extra language, add `fr.ts` with `export const fr = { … } satisfies Record<MessageKey, string>;`, so a missing key is a type error. Add it to `MESSAGES` and `LOCALES` in `index.ts` and to the `language` group's options.
3. Format numbers, money and dates with `formatNumber`/`formatDate` (or `Intl` with `locale`), not `toFixed` or string concatenation. Formats changing with the language is half of why the setting is useful. For money, use `Intl.NumberFormat(locale, { style: 'currency', currency, currencyDisplay: 'narrowSymbol' })`. Without `narrowSymbol`, a currency foreign to the locale gets a disambiguated symbol, such as "12,95 £GB" in French or "US$" in English.
4. Translations: write them if the user asked for those languages. Say they're machine-drafted and should be checked by a native speaker before anything ships.

When a sentence has a styled value in the middle ("You have **£20** left"), keep the whole sentence as one message with a placeholder. Splitting it into pieces breaks languages that order words differently. Render it by splitting the template on `{name}` and styling the filled-in parts.

## B. i18next / react-i18next

Keep i18next. Make the dev setting drive it by adding a small effect in the root layout component:

```tsx
import i18n from '<the app's i18n instance>';
import { useDevSettings } from '../preview/devSettings';

const { language } = useDevSettings();
useEffect(() => {
  if (i18n.language !== language) i18n.changeLanguage(language);
}, [language]);
```

`react-i18next` re-renders components using `useTranslation()` when the language changes, so nothing else is needed. Use the same language codes in `devSettings.ts` as the i18next resources (`'en'`, `'fr'`, or `'en-GB'` if that's how they're keyed).

Only do this when the app is in the preview, so device builds keep detecting the language: wrap the effect body in `if (isEmbeddedInPreview())`, imported from `preview/previewBridge`. If the team also wants to switch language on devices from a dev menu, drop that check.

## C. expo-localization only (device locale picks the language)

Usually there's a helper like `getLocales()[0].languageCode` feeding a lookup. Change it so that inside the preview, the dev setting wins:

```ts
const language = isEmbeddedInPreview() ? getDevSettings().language : getLocales()[0]?.languageCode ?? 'en';
```

If it's read once at startup, it won't update live. Move it into a hook that reads `useDevSettings()`, so components re-render when the setting changes.

## D. Lingui, react-intl, others

The same idea applies. Find the single place the active locale is set (`i18n.activate(locale)` for Lingui, `<IntlProvider locale>` for react-intl) and feed it from `useDevSettings().language` while embedded in the preview. Rendering the provider from a component that reads `useDevSettings()` is enough for live updates.

## Check

Switch language in the panel and confirm, without reloading:
- copy changes on the current screen and on screens you navigate to,
- numbers and dates use that language's format (`1,862.40` / `1 862,40` / `1.862,40`),
- long translations (German is a good test) don't overflow buttons or headers. If they do, tell the user; that's a real finding the preview is for.
